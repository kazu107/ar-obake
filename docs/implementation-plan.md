# ARおばけ探偵団 Webアプリ 実装計画

作成日：2026-09-10

状態：0.5.0と複数台の会場リハーサルを利用者が確認し、受け入れ済み。0.6.0でMission v2、スタッフ画面、次グループへのリセット、PWA、明示的なオフライン準備を実装し、PCでオフライン再起動まで確認した。次は0.6.0のiPad実機確認と最終素材での本番判定。最新の進捗は[staff-offline-0.6.0.md](staff-offline-0.6.0.md)を参照。

参照：[枝分かれ · メタバース企画内容](chatgpt-conversation://6a672ea1-b758-83ee-a2b0-a401f7cbc27b)の最新の仕様書と、その直前のユーザー要望。

## 1. 目的と現在地

小学生が1人1台のiPadで画像マーカーを探し、ARのおばけからヒントを集める。各自の捜査メモを持ち寄って相談し、代表者が回答専用マーカーからアイテムの色と種類を回答する。正解表示から、現実のおばけをボールで撃退する体験へつなげる。

計画策定時は空の作業フォルダから開始した。現在はVite・TypeScript・MindARの実装とGit履歴がある。

開発の順序は「実機でARが成立するか確認 → 小さなゲームを最後まで遊べる状態にする → 本番問題・素材へ拡張 → 復帰・オフライン・会場試験」とする。

## 2. 要望と初期の設計判断

### ユーザーが明示した要望

- Webアプリとして作り、iPad Air 2を使用する予定。
- 最初はMindARなどを使った画像認識ARで試す。
- ヒントは色とアイテムの種類に限定し、肯定・否定・複合条件を扱う。
- 集めた情報をアイコンと○・×・？で記録する。
- 全員で情報を持ち寄る時間を設け、代表者が回答用マーカーを読み取って答える。

### この計画で置く初期設定

| 項目 | 初期設定 |
| --- | --- |
| 色と種類 | 緑・ピンク・青・黄色 × メガネ・リボン・帽子・手袋。Missionデータで変更可能 |
| 色の意味 | アイテムの色。画面文言を「アイテムは何色？」に統一 |
| 本番問題 | まず1つのMission、8ヒント＋回答1枚を完成させる |
| 参加者の情報 | 各端末で取得した情報だけを保存し、共有は人同士で行う |
| 協力の成立方法 | スタッフが探索場所を分担し、1人1～3枚程度の取得を案内する |
| 回答への移動 | 「みんなと相談する」→共有画面→代表者が「回答マーカーを読む」→ANSWER認識 |
| 探索中のANSWER | 相談後に読むよう案内し、その場で回答画面へ飛ばさない |
| 代表者の扱い | スタッフの進行で決める。アカウントや端末の代表者認証は設けない |
| ヒントの取得 | 0.4.0から安定認識後に自動記録。短い誤認識では保存せず、同じカードは重複させない |
| 再回答 | 回数制限・ペナルティなし。メモの確認に戻れる |
| 時間管理 | 当初はスタッフの声かけと画面ボタン。端末間の一斉タイマーは設けない |

「必ず1人では解けない」ことは、この初期設定ではシステムとして保証しない。1人が多数のマーカーを読めば解けるためである。厳密な制限が必要になった場合は、担当グループ別の取得権限などを別途設計する。

企画名、最終的な色・アイテム、グループ人数、端末台数、会場照明、設置距離、配信先は本番準備までに確定する。これらが未確定でも基盤と試作は進められる。

## 3. 技術方針

- Vite＋TypeScript＋通常のHTML/CSSを基本とする。
- 最初の検証候補はMindAR 1.2.5＋Three.js 0.160.0。これは[MindAR公式導入例](https://hiukim.github.io/mind-ar-js-doc/installation/)にも登場する組み合わせであり、Air 2での動作保証を意味しない。
- Vite・Node・テストツールのバージョンは基盤作成時に対応関係を確認し、lockfileとREADMEに固定する。「最新」という名称だけで選ばない。
- Safari 15をビルド対象の初期設定とし、実機のOSバージョンも記録する。[Vite公式のbuild.target](https://vite.dev/config/build-options)で対象を明示する。構文変換と、Web API・GPUの対応可否は別に確認する。
- import mapに依存せず、npm由来の依存をビルドへ取り込む。MindARの内部Workerや追加ファイルも含め、生成物からの読み込みを確認する。
- 必要なライブラリ・画像・GLB・認識データ・音声を同じサイトから配信できるようにする。
- カメラを使う実機試験用URLはHTTPSで用意する。[getUserMediaの利用条件](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)を踏まえ、iPadからPCのHTTPアドレスを開くだけの構成にはしない。
- ゲームの進行にサーバーAPI・DB・ログインは使わない。
- AR認識は交換可能な入口とし、MindARでの検証結果が厳しい場合にQR認識＋画面上のおばけ表示を検討できる構造にする。

## 4. 段階ごとの実装と完了条件

### Phase 0：開発基盤と検証方法を用意する

作業：

- Git初期化、.gitignore、Vite＋TypeScriptの最小構成、依存バージョンの固定。
- 型チェック・production build・ゲームロジックのテストを実行するコマンドを用意する。
- AR、ゲーム、UI、保存、問題データの境界を決める。
- 仮マーカー・仮GLBを用意し、出典または生成元を記録する。
- HTTPSの実機確認用URLと、端末で試す短い手順を用意する。配信先は利用可能な環境を確認して選定する。
- 実機記録表を用意する。端末・OS・アプリの版・マーカーセット・起動時間・認識時間・エラーを残す。

完了条件：production buildが作成でき、PCで開始画面を開ける。Air 2で開くためのURLとマーカーがそろう。

### Phase 1：MindAR＋Air 2の成立を早期に確認する

作業：

- 開始操作、カメラ許可、背面カメラ映像、読み込み表示、認識状態の表示を実装する。
- 1マーカーの認識と、軽量GLBの追従表示を実装する。
- カメラ・レンダラーを重複作成しないよう、開始／停止／破棄を管理する。
- マーカーの発見・喪失、カメラ拒否、初期化失敗、バックグラウンドからの復帰を確認する。
- 仮画像で1枚→4枚→9枚の認識セットを作り、ゲーム本体を作り込む前に負荷を調べる。
- マーカー画像の順序とtargetIndexの対応を保存する。[MindAR公式の事前コンパイル手順](https://hiukim.github.io/mind-ar-js-doc/quick-start/compile/)を基に、再生成できる手順を残す。

完了条件：

- Air 2実機で、1枚と9枚のセットそれぞれで10分連続動作を確認する。
- 権限許可済み・必要素材をキャッシュ済みの状態で、開始操作からAR準備完了まで10秒以内を目安とする。初回ダウンロード時間と人が許可するまでの時間は別に記録する。
- 想定の印刷サイズ・明るさ・距離で、各マーカー10回のうち9回以上を3秒以内に認識できることを初期目標とする。未検出・誤認識も記録する。
- 読み取りとUI操作を続けても、クラッシュ・勝手なページ再読み込み・進行不能がない。

目標未達の場合：素材、描画解像度、カメラ設定、同時表示数、認識設定を調整して再測定する。記録を基にMindAR継続かQR方式への変更案を判断する。PCで成功しただけでは、この段階を実機合格にしない。

### Phase 2：ヒント・推理・保存の核を作る

作業：

- Missionの型と読込時の検証を作る。ID、版、選択肢、正解、ヒント、markerId、targetIndex、素材参照を定義する。
- ヒントの表示文と条件データを分け、条件の側で候補を絞る。
- ○・×・？への変換、残り1候補の自動確定、矛盾検出、重複取得の防止を実装する。
- 取得済みmarkerIdを基に状態を再計算できるようにする。
- 最低限のlocalStorage保存をこの段階から入れ、schemaVersion・missionId・missionVersionを持たせる。
- ARを使わずマーカー発見を再現できる開発用入口を用意する。本番ビルドには表示しない。

意味のある自動テスト：

- 肯定・否定・色と種類をまたぐ複合ヒント。
- 取得順序によらず同じ結果になること、同じヒントで結果が増えないこと。
- 全候補除外、矛盾する肯定、未知のIDを検出し、壊れた結果を保存しないこと。
- 保存から復元しても同じメモになること。

完了条件：カメラなしで複数ヒントを入力し、正しい候補・正誤判定・復元を確認できる。別の端末の取得情報は反映されない。

### Phase 3：4枚のマーカーで一通り遊べる試作を完成させる

作業：

- 開始、説明、探索、ヒント表示、メモ、共有、回答マーカー読取、色選択、種類選択、確認、正解・不正解をつなぐ。
- 探索画面には小さな捜査メモを表示し、タップで拡大できるようにする。
- ヒントは明示的な記録操作で保存する。取得前のマーカー喪失時は表示を解除し、取得済みの情報は保持する。
- 共有画面でその端末の情報を大きく見せる。回答後もメモへ戻れるようにする。
- 連続する認識イベントや連打で画面が重複遷移しないようにする。
- 説明・共有・回答中は不要な追跡や描画を止め、再スキャン時に復帰する。

試作用の正解は「青い帽子」とし、次の3ヒントで色と種類の両方を確定させる。

| マーカー | 条件 |
| --- | --- |
| H01 | 緑ではない、眼鏡ではない |
| H02 | 黄色ではない、手袋ではない |
| H03 | ピンクではない、リボンではない |
| ANSWER | 回答用 |

これは小規模な動作確認用Missionであり、本番の協力バランスを保証する問題ではない。元の仕様書の色だけのPoCを、完成版の「色＋種類」まで確認できる形に広げる。

完了条件：Air 2で開始→取得→共有→回答→誤答から再回答→正解を通せる。別々の端末に違うメモが残り、人が相談して回答できる。

### Phase 4：本番用の問題・マーカー・見た目へ拡張する

0.6.0の進捗：色とアイテムを最終候補へ変更し、答えを青い帽子に固定。8ヒントの構造と難易度を維持し、全256集合を再検証した。自動記録、効果音、全画面カメラ、3D吹き出し、下部メモ、TUTORIALも継続する。

作業：

- 本番Missionを8ヒント＋ANSWERにする。将来の別Missionはデータの追加で扱えるようにする。
- 全ヒントが正解と整合し、全体で答えが一意に決まり、1枚だけでは色と種類の両方が判明しないことを検証する。
- 全部分集合を列挙し、何枚・どの組み合わせで解けるかをレポートする。
- 問題バランスの初期目標は「どの1枚を取り逃しても解ける」「6枚の組み合わせの80%以上で解ける」とする。5枚の場合の割合・最小必要枚数も記録し、スタッフの分担と合わせて調整する。
- 色・アイテムのアイコン、ひらがなを中心とした文言、押しやすいボタンを整える。
- 低負荷なおばけの浮遊、ヒント取得、正解時の演出と短い効果音を追加する。音を再生できなくても進行できるようにする。
- GLBは1MB以下を当初の目標とし、1体を共有、影なし、少ないマテリアル・小さいテクスチャから始める。
- A5～A4印刷用マーカー9枚と対応する.mindを制作する。デザインの違いと特徴点を確認する。
- マーカー画像・コンパイル順・Mission・.mind・アプリの版を対応づける。印刷物と認識対象が一致することを確認する。

完了条件：本番の9枚でゲームが成立し、問題検証が通る。印刷マーカー、GLB、UI、実物のアイテムの色・種類が一致する。最終素材でもPhase 1の性能目標を再確認する。

### Phase 5：復帰とスタッフ運用を仕上げる

0.6.0でスタッフ画面、状態表示、開始時刻・経過時間、確認付きの次グループ用リセットを実装。PCのブラウザ通し操作に合格。

作業：

- 起動時の「続きから／最初から」、確認つきリセット、スタッフ画面を実装する。
- スタッフ画面にはMission・アプリの版、取得ヒント、開始時刻、カメラ状態、FPSなどを表示する。これは認証機能ではなく、通常画面から操作を分けるための入口とする。
- 保存形式の不正、Missionの版の違い、保存失敗を検出する。異なる問題のデータを黙って流用しない。
- 一時的なAR状態や3Dオブジェクトは保存せず、復帰後は必要に応じてカメラを起動し直す。
- Safari再読み込み、ホーム画面へ移動して復帰、画面回転、カメラ権限拒否・再許可を確認する。
- 次のグループへ渡す際、取得済み情報と回答結果がリセットされることを確認する。

完了条件：中断後もメモを復元でき、カメラやボタンが二重に動作しない。スタッフが次のグループの開始まで自力で操作できる。

### Phase 6：オフライン動作と配信を仕上げる

0.6.0でmanifest、Service Worker、版別キャッシュ、スタッフによる明示的なオフライン準備を実装。PCでは準備後に通信を切り、スタッフ画面・ゲーム・Mission v2を再読み込みできた。iPad実機でのオフラインAR通し操作は未確認。

作業：

- manifestとService Workerを追加する。[Service Workerの導入・更新・キャッシュ管理](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers)を踏まえて実装する。
- HTML、JSの分割ファイル、CSS、Worker、Mission、.mind、GLB、画像、音声を事前キャッシュ対象にする。
- 必要な素材がそろったときだけ、スタッフ向けに「オフライン準備完了」を表示する。
- イベントの途中で新旧のアプリ・問題・認識データが混ざらないよう更新を管理する。プレイ中に自動で再読み込みしない。
- 配信用buildを実際のHTTPS URLで確認し、サブパス配置がある場合も素材が取得できるようにする。
- 初回オンライン準備後、通信を切ってページを再読み込みし、探索から正解まで試す。

完了条件：準備済みAir 2で通信を切り、再読み込み・AR・全ヒント・回答・効果音まで動作する。キャッシュ不足時は準備未完了が分かる。

注記：PWAのインストールとオフライン準備は別に確認する。一度開いたという事実だけでは準備完了にしない。本番当日も端末ごとに確認する。

### Phase 7：会場に近い条件で本番判定する

作業：

- 最終build・最終印刷マーカーで10分連続試験を最低10回行う。
- マーカーの連続50回認識、同じマーカーの再認識、似た柄による誤認識を確認する。
- 明暗・斜め・反射・50cm・1mで調べ、使用可能な距離と設置方法を運用手順に記録する。
- 複数台で起動し、個別保存・相談・代表回答・次グループへのリセットまで通す。
- 本番で使う全端末について、OS、充電、カメラ、読取、キャッシュ、リセットを確認する。
- 低学年を想定した操作確認を行い、説明込みのイベント全体が約10分に収まるよう調整する。
- 読み取れない場合の予備ヒントカード、端末準備手順、当日の進行台本、障害時の復帰手順を用意する。

完了条件：重大な進行不能・クラッシュ・誤判定がなく、実機記録が残る。本番担当者が手順書に沿って開始・進行・復旧・リセットできる。

## 5. 構成の目安

以下は実装時に作成する予定の構成であり、現在存在するファイル一覧ではない。

```text
src/
  ar/          # 認識・カメラ・3D表示。発見と喪失を通知
  game/        # 進行、ヒント演算、回答判定、Mission検証
  ui/          # 画面、捜査メモ、回答UI、スタッフUI
  storage/     # 保存と復元、保存形式の版管理
  data/        # 型・Mission読込
  styles/
public/
  missions/    # Mission JSON
  targets/     # .mindと画像順の対応表
  markers/     # 認識対象画像
  models/
  icons/
  audio/
assets/source/ # 編集元・生成元・素材出典
scripts/       # 問題検証・マーカー生成支援
tests/         # ヒント演算、復元、画面遷移の重要経路
docs/          # 計画、試験結果、印刷・実機・運用手順
```

ARからゲームへの通知はmarkerIdを中心とする。位置合わせなどの表示責務はAR側に閉じ込める。QRへ変更する場合、認識器に加えておばけの表示位置の扱いも変更し、ヒント演算・Mission・保存・回答画面を再利用する。

## 6. 検証と進行管理

- 各段階の完了時に、該当する型チェック・build・自動テスト・画面確認を行い、結果を記録してGitへコミットする。
- 自動ブラウザ試験は、開発用の認識イベントを使ってゲームの流れ・復元・二重登録を確認する。実際のカメラ認識の成功を代替しない。
- PCのブラウザやWebKit系の自動試験はAir 2実機と区別して報告する。
- 実機が手元にない期間はPhase 2のロジックやPhase 3の画面実装を進められる。ただし、Phase 1の合格と本番利用可能の判定は保留にする。
- 新しい素材、依存更新、認識設定の変更など、性能に影響する変更が入ったときに実機試験を追加する。
- 日数はPhase 1で実機と配信経路を確認してから見積もる。まず「AR検証版」「一通り遊べる試作」「本番候補版」の3つを到達点とする。

## 7. 最初の実装で納品するもの

最初はPhase 0～1に集中し、以下を用意する。

1. Vite＋TypeScript＋MindAR＋Three.jsの最小プロジェクト。
2. 開始ボタンからカメラを開き、マーカー上に仮のおばけを表示する検証画面。
3. 1枚・4枚・9枚の検証用マーカーセットと、印刷・コンパイルの対応表。
4. 起動時間・認識・連続動作を確認する表示と試験記録表。
5. Air 2で開けるHTTPSの確認用URLと操作手順。

この検証結果を、完成版の実装を進めるための最初の判断材料とする。
